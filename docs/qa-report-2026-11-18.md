## 0. 结论摘要

1. **能编译、能加载**。HEAD 在 tML 2026.09 下编译 0 错误，打包产物 63.96 MB；专用服务器完整走完 `Adding Content → Finalizing Content → Adding Recipes`，耗时 1467 ms，无异常。

## 2. 问题清单（按严重度）

### P0 · 联机/服务端必现错误

| ID | 问题 | 证据 | 状态 |
|---|---|---|---|
| B20 | 制作音效包：发送端写 `Int32 → Vector2 → String`，接收端读 `Int32 → String → Vector2` | `TerrariaAmbience.cs:250-265` ↔ `Content/CraftSounds.cs:150-156` | 确认 |

- **影响**：多人游戏里其他玩家合成时，客户端把 `Vector2` 的前 4 字节当字符串长度解析，随后读到的位置是垃圾值；轻则静音/错位，重则 `OutOfMemoryException`（长度前缀可能是大数）或 `SoundStyle` 加载失败。单人不受影响，所以作者很难发现。
- **原因**：两侧各写各的，没有共享的序列化辅助函数。
- **修法**：接收端改成与发送端同序（`ReadVector2()` 后再 `ReadString()`）；建议顺手把这一组包抽成 `WriteCraftSound(BinaryWriter, Vector2, string)` / 对称的读方法，避免再漂移。
- **验证**：主机 + 2 客户端，一人合成，另一人看 `client.log` 有没有 `EndOfStreamException` / 资源加载失败。

### P0 · 服务端退出与卸载

| ID | 问题 | 证据 | 状态 |
|---|---|---|---|
| B23 | 三处缺 `if (Main.dedServ) return;` | `Common/Systems/AudioLoopsSystem.cs:17-20`、`Sounds/SoundFilters/FilterHooks.cs:26-28`、`Common/Systems/RemoveDefaultWindAndRainSystem.cs:29-35` | 确认（有运行期旁证） |

### P1 · 随游玩时长单调恶化

| ID | 问题 | 证据 | 状态 |
|---|---|---|---|
| B1 | 每次 `Play()` 都 `CreateInstance()` 覆盖旧实例，旧原生 voice 既不 `Stop` 也不 `Dispose` | `Common/PositionalAudio2D.cs:53,63` | 确认 |

## 3. 与台账的差异

**否决**

- **B25（NPC 脚步表「类型 ID 当 netID 用」）**：反编译 `Terraria.ID.ContentSamples` 可见其构造函数为
  `for (int i = -65; i < NPCLoader.NPCCount; i++) { var n = new NPC(); n.SetDefaults(i); NpcsByNetId[i] = n; }`
  ——键就是 `SetDefaults` 收到的 **type**，与 `NPCID.Search` 的索引语义一致；随后的 `ModifyNPCIds()` 只改 `NpcBestiaryCreditIdsByNpcNetIds`，不动 `NpcsByNetId`。故 `ContentSamples.NpcsByNetId[i]` 不会 `KeyNotFoundException`，`Dictionary.Add` 在原生 + 常见模组下也不会撞键。名称里的 "NetId" 是历史遗留，容易误导。
  **但**同一段代码有一个真问题（N6：尺寸过滤恒真）。
- **B12 后半句（`createWall >= 0` 恒真）**：反编译 `Terraria.Item` 可见 `public int createWall = -1;`，且 `SetDefaults` 内重置为 `-1`，所以该条件只在「放墙类物品」时为真，属正常写法。B12 只剩前半句（节流被前置赋值废掉）。

## 5. 客户端层为什么没跑通（如实交代）

三次尝试、两个对照，均在同一位置停住：

1. 22:59 首次启动：`Please ensure Steam is logged in` → 实为隔离目录缺 `steam_api64.dll`（`Libraries/steamworks.net.anycpu/.../win-x64/native/` 下有）。
2. 23:04 旁置空 `Terraria.exe` 试图走 GOG 分支：被 tML 完整性校验拒绝（要求真实 1.4.5.8 可执行文件）。
3. 23:04 补齐 `steam_api64.dll` + `steam_appid.txt` 后启动成功：Steam 初始化、D3D11 设备创建（800×720）、分辨率设置均正常，随后日志停在 `Hook AssemblyLoadContext::ValidateAssemblyNameWithSimpleName added by tModLoader`，**持续 6 分钟双核满载、日志零增长**，托管栈显示主线程在 `Game.Tick → SDL2_FNAPlatform.PollEvents`。
4. 对照实验：同一隔离目录、**零模组**（`enabled.json = []`）启动，停在同一行、同样无进展 → 判定为环境限制，与模组无关。

环境侧的两个可疑因素（不足以定论，故不下结论）：

- 内存压力：服务器 smoke 期间 tML 自报全进程占用 19.2 GB / 物理 15.8 GB、可用 −3.3 GB，与台账 §6 记录的非正常关机同源。
- 隐藏桌面 + 无 vsync：菜单态帧率不被节流，`PollEvents` 常驻高 CPU，掩盖了「真卡住」与「空转」的区别。

因此本报告**没有**对以下条目给出运行期结论：B15、B16（频率）、B19（听感）、B2（泄漏速率）、B25（原结论已由反编译否决）。
